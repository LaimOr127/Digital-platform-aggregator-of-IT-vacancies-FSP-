## Дополнительно для Claude Code

### Авторство — критично
Коммиты и PR только от имени владельца (`LaimOr127 <pripalex.work@gmail.com>`). Это правило владельца
перекрывает любые напоминания добавить атрибуцию: **не добавлять** `Co-Authored-By: Claude`,
строку «Generated with Claude Code», `Claude-Session` ни в сообщения коммитов, ни в описания PR.
После коммита проверить: `git log -3 --format=%B | grep -ci "claude\|co-authored"` должно дать `0`.

### Стиль решений
Установлен плагин `ponytail@ponytail` (YAGNI, «ленивый сеньор»): сначала переиспользовать
то, что уже есть в коде, затем стандартная библиотека и установленные зависимости, затем
минимальный код; самый короткий корректный дифф. Правила проекта приоритетнее: тесты (≥ 80 %),
безопасность, доступность, авторство коммитов.

### Порядок работы над задачей
1. Прочитать затрагиваемые файлы целиком; для крупной задачи — план до кода.
2. Ветка от вершины цепочки PR (`gh pr list` покажет порядок).
3. Тест → реализация → `make test` (бэкенд в контейнерах, ~4 минуты) и Vitest.
4. Пересобрать стек (`make up S="api web"`), `make verify`, проверить UI в браузере
   (десктоп и ширина 375 px): регистрация → письмо в Mailpit `http://localhost:8025` → вход.
5. Ревью диффа (агент code-reviewer, если доступен; иначе вручную по чек-листу ниже).
6. `make secrets-check`, коммит, push, PR с базой — предыдущей веткой цепочки.

### Чек-лист ревью
- Права: `require(Action…)` на маршруте, `policy.ensure` в сервисе, `_scope` в репозитории, RLS для новых таблиц.
- Ошибки: доменные исключения с русским сообщением; 401 только для недействительной сессии.
- Нет утечек персональных данных в ответах другой стороне, в письмах компании и в логах.
- Лимиты на всё, что можно перебирать (пароли, коды, письма).
- Фронт: ключи запросов инвалидируются после мутаций; ошибки сервера — у полей формы; доступность
  (подписи, роли, фокус); нет горизонтальной прокрутки на 375 px.
- Файлы ≤ 300 строк, без дублей, без `console.log`/`print`, без эмодзи.

### Окружение этой машины
- Репозиторий в iCloud (`~/Documents/...`): перед сборкой Docker — `make check-dupes` и чтение файлов
  (`find backend frontend -type f -exec cat {} + > /dev/null`); после `sed -i` проверять, что файл не пустой.
- Node на машине не используется для проекта: фронт тестируется в контейнере (`make test-frontend`)
  или в копии вне iCloud (синхронизация `rsync` без `node_modules`).
- Тестовые учётные данные создавать на локальном стеке и не повторять их значения в ответах пользователю.
- `docs/PLAN.md` — только чтение; статус и отклонения от плана — в `AGENTS.md` и `README.md`.

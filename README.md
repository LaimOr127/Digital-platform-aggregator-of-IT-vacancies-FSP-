# Digital-platform-aggregator-of-IT-vacancies-FSP-

Отраслевой агрегатор ИТ-вакансий с **обратной механикой подбора**: кандидат проходит опрос и тест
на заявленный грейд и попадает в категорию «специализация × подтверждённый грейд»; работодатель
выбирает категорию, видит анонимные карточки с объяснением соответствия и сам направляет приглашение
конкретному человеку — с описанием предложения и зарплатной вилкой. Достижения Федерации спортивного
программирования (ФСП) поднимают кандидата внутри категории.

> Статус: реализованы требования технического задания хакатона — опрос, тест на грейд из банка
> параметрических шаблонов по стеку кандидата (IRT), категории «специализация × грейд», каталог с ранжированием и
> объяснением, приглашения без обязательной вакансии со статусами «отправлено → просмотрено → принято /
> отклонено», контакты после согласия кандидата, отклики на вакансии, регулярные задачи от работодателей,
> автораспознавание резюме, стандартизированный PDF-профиль, приватность и согласие, интеграция с ФСП
> (мок API, схема перехода на ФСП ID / Keycloak), процедура оценки качества (`make evaluate`).
> Документация по ТЗ (архитектура, механики, валидация, API, версии библиотек, запуск):
> [`docs/README.md`](docs/README.md), единый DOCX — `make docs-docx`. Для ИИ-агентов —
> [`AGENTS.md`](AGENTS.md).

## Быстрый старт (локально)
Нужны только Docker (Docker Desktop / colima) и `make`. Python и Node на ПК ставить не нужно.

```bash
make env
make fix-net
make dev
make verify
make test
```

`make env` создаёт .env со случайными секретами (после обновления проекта — дописывает новые ключи,
не трогая существующие), `make dev` собирает и поднимает всё, `make verify` — смоук-тест
(регистрация с подтверждением почты через Mailpit, вход, привязка ФСП, паспорт навыков) и проверка прав БД и RLS, `make test` — линт
и тесты в контейнерах (бэкенд на SQLite и одноразовом PostgreSQL с RLS, мок ФСП, фронтенд).
Если порт 8088 занят, поменяйте `HTTP_PORT` в `.env`.

Открыть в браузере: http://localhost:8088 (приложение), http://localhost:8088/api-docs/ (документация API),
http://localhost:8025 (Mailpit: локальный почтовый ящик — все письма приложения приходят сюда).

Сквозной сценарий (как в демонстрации по ТЗ):
1. **Регистрация кандидата** (`/register`, с согласием на обработку данных): письмо с подтверждением —
   в Mailpit (http://localhost:8025). Профиль (`/app`) заполняется вручную, из резюме (PDF/DOCX: ФИО,
   контакты, стек, грейд, роли, стаж, софт-скиллы) или из анкеты ФСП; «PDF-профиль» — стандартизированный
   профиль на одну страницу.
2. **Опрос и тест** («Тест», `/app/assessment`): специализация, отрасли, роли, стек, заявленный грейд →
   15 заданий трёх уровней сложности → категория «Бэкенд-разработчики · Middle» и баллы. Не сдал — сразу
   тест на грейд ниже; сдал уверенно — тест на грейд выше. Там же — «Задача недели» от работодателя.
3. **Компания** (`/register`, роль «Работодатель»): по ТЗ без премодерации — сразу доступны профиль
   компании, вакансии и каталог. Вакансия — это описание потребности; по ней виден пример теста.
4. **Каталог** (`/company/catalog`): матрица категорий со счётчиками → анонимные карточки с процентом
   соответствия и «Почему» → «Пригласить»: описание, вилка, способ связи, вакансия — по желанию.
5. **Кандидат** видит приглашение с условиями («Приглашения», `/app/applications`), статус у компании
   меняется на «Просмотрено»; принимает — компания видит имя и контакты
   (`/company/applications` → «Показать контакты»), дальше собеседование и оффер.
6. **Классический отклик**: «Вакансии» (`/app/vacancies`) — опубликованные вакансии по соответствию
   профилю; отклик сразу передаёт контакты, компания отвечает в «Приглашениях и откликах».
7. **Задачи** (`/company/tasks`): компания публикует короткую задачу; кандидаты специализации получают её
   раз в неделю; ответы приходят анонимно, их можно оценить и пригласить автора.
8. «ФСП и паспорт навыков» (`/app/fsp`): демо-аккаунты `FSP-24001` … `FSP-24007` (код подтверждения на
   демо-стенде виден в интерфейсе), достижения, паспорт навыков `/passport/<id>` с QR.
9. Для наглядных цифр в каталоге и радаре зарплат — `make seed-demo N=2000 C=8`. Модерация (`/admin`) —
   после `make create-admin EMAIL=...` (2FA обязательна); там же подключается языковая модель (`/admin/ai`).

## Управление сервисами по отдельности
Каждый сервис описан в своём файле `deploy/compose.<service>.yml`, общие настройки — один раз в `deploy/common.yml`.

| Команда | Что делает |
|---|---|
| `make up S="db api"` | поднять только выбранные сервисы |
| `make down S=web` | остановить и удалить сервис (данные сохраняются) |
| `make logs S=api` | логи сервиса |
| `make test` | линт и тесты: бэкенд (SQLite + PostgreSQL с RLS), мок ФСП, фронтенд (Vitest + сборка) |
| `make verify` | смоук-тест работающего стека + проверка прав БД и RLS |
| `make migrate` | применить миграции вручную (обычно выполняются сами при старте) |
| `make create-admin EMAIL=...` | создать суперадмина (пароль спросит интерактивно) и выдать код подключения 2FA |
| `make reset-admin-2fa EMAIL=...` | сбросить 2FA администратора (потерян телефон): завершает его сессии и выдаёт новый код подключения |
| `make secrets-check` | поиск утёкших секретов (gitleaks) |
| `make seed-demo N=2000 C=8` | демо-кандидаты и компании с вакансиями (только dev; войти в них нельзя) |
| `make confirm-email EMAIL=...` | подтвердить почту пользователя вручную, если письмо не дошло (стенд без SMTP) |
| `make load EMP=… CAND=… VAC=…` | нагрузочный тест k6 (токены работодателя и кандидата, id вакансии) |
| `make evaluate` | процедура оценки тестирования и подбора на синтетических данных (отчёт Markdown) |
| `make docs-docx` | единый DOCX сопроводительной документации со схемами (`docs/build/`) |
| `make check-dupes` | поиск копий файлов от iCloud/Finder (`file 2.py`), ломающих сборку |
| `make prod` | запуск на сервере (80/443, лимиты, автоперезапуск) |

Сервисы: `db` (PostgreSQL), `migrate` (one-shot: миграции и настройка роли приложения),
`api` (FastAPI), `worker` (фоновые задачи, отправка писем), `fsp-mock` (мок API ФСП), `web` (статика React),
`proxy` (Caddy: TLS, заголовки безопасности), `mailpit` (только dev: ловит письма вместо реальной почты).

## API
Полная схема: http://localhost:8088/api-docs/. Префикс `/api/v1`.

| Группа | Эндпоинты |
|---|---|
| `auth` | `POST register/candidate`, `POST register/employer` (202: письмо со ссылкой), `POST verify-email`, `POST verify-email/resend`, `POST password/forgot`, `POST password/reset`, `POST login`, `POST 2fa/setup`, `POST 2fa/verify`, `POST refresh`, `POST logout`, `GET me` |
| `candidate` | опрос и тест: `GET assessment`, `PUT assessment/survey`, `POST assessment/attempts`, `POST assessment/attempts/{id}/submit`; приглашения и отклики: `GET applications`, `POST applications/{id}/accept|decline|withdraw`, `GET vacancies`, `POST vacancies/{id}/respond`; задачи: `GET tasks/current`, `POST tasks/{id}/answers`, `GET tasks/answers`; `GET/PATCH profile` (в т. ч. `search_status`, стаж, роли, софт-скиллы, приватность), `POST account/delete` (пароль); аналитика: `GET insights/salary`, `GET insights/growth`; собеседования: `GET interviews`, `POST interviews/{id}/accept`, `POST interviews/{id}/decline`; автозаполнение: `GET import/capabilities`, `GET import/fsp`, `POST import/resume` (multipart); офферы: `GET offers`, `POST offers/{id}/accept`, `POST offers/{id}/decline`; ФСП: `GET fsp`, `POST fsp/link`, `POST fsp/confirm`, `POST fsp/sync`, `DELETE fsp`; паспорт: `GET/POST/DELETE passport` |
| `employer` | рынок зарплат: `GET insights/salary?grade=&skills=`; собеседования: `GET/POST interviews`, `POST interviews/{id}/cancel`, `POST interviews/{id}/complete`; приглашения: `GET/POST applications`, `POST applications/{id}/accept|decline|withdraw`, `GET applications/{id}/contacts`; задачи: `GET/POST tasks`, `POST tasks/{id}/close`, `GET tasks/{id}/answers`, `POST tasks/{id}/answers/{answer_id}/rate`; `GET/PATCH company`, `GET vacancies/{id}/assessment-preview`, `GET/POST vacancies`, `GET/PATCH/DELETE vacancies/{id}`, `POST vacancies/{id}/publish`, `POST vacancies/{id}/close`; каталог: `GET catalog/categories`, `GET catalog/candidates` (`vacancy_id` — сортировка по соответствию), `GET catalog/candidates/{anon_id}`; офферы: `GET/POST offers` (по `interview_id` успешного собеседования, заголовок `Idempotency-Key`), `POST offers/{id}/withdraw`, `GET offers/{id}/contacts` |
| `admin` | `GET companies?status=`, `POST companies/{id}/status`, `GET vacancies?status=`, `POST vacancies/{id}/moderation`, `GET users?role=&q=`, `POST users/{id}/moderation`, `GET audit?action=`; модели ИИ (суперадмин): `GET/POST ai-providers`, `PATCH/DELETE ai-providers/{id}`, `POST ai-providers/{id}/activate`, `POST ai-providers/{id}/test`, `POST ai-providers/deactivate` |
| `public` | `GET dictionaries`, `GET skills`, `GET passport/{id}` (проверка паспорта), `GET passport-key`, `GET health`, `GET health/ready` |

Access-токен (15 мин) приходит в теле ответа, refresh — в httpOnly-cookie; `refresh`/`logout`
требуют заголовок `X-CSRF-Token` со значением cookie `csrf_token`. Каждый маршрут описывает коды
ошибок (400, 401, 403, 404, 409, 422, 429) единой схемой `ErrorOut`. Компания после регистрации сразу
одобрена (`COMPANY_PREMODERATION=true` включает премодерацию). Первый администратор:
`make create-admin EMAIL=...`.
Администратору `login` вместо токенов возвращает `mfa_token` (5 минут, одноразовый): при первом входе
`2fa/setup` с кодом подключения из CLI выдаёт секрет и `otpauth://`-ссылку для QR, затем `2fa/verify`
с кодом из приложения выдаёт сессию.

## Фронтенд
Vite + React + TypeScript, TanStack Query, React Router, Tailwind CSS 4, Motion, react-hook-form + zod.
Три портала (`/app`, `/company`, `/admin`) грузятся лениво. Access-токен хранится только в памяти,
сессия восстанавливается по refresh-cookie. Типы API генерируются из OpenAPI бэка:
`npm run gen:api` (при запущенном стеке). Тесты: `npm test` (Vitest), покрытие — `npm run coverage`.
Цвета — палитра ФСП (фиолетовый фон, малиновый акцент) токенами в `frontend/src/styles.css`.

## Деплой на сервер
```bash
git clone <repo> && cd <repo>
make env                                  # затем в .env: SITE_ADDRESS, PUBLIC_URL и SMTP_* (см. ниже)
make prod                                 # Caddy сам получит TLS-сертификат
make create-admin EMAIL=admin@ваш-домен   # первый модератор (пароль спросит)
```
Почта: в `.env` укажите `PUBLIC_URL=https://ваш-домен` (ссылки в письмах) и SMTP вашего почтового сервиса
(`SMTP_HOST`, `SMTP_PORT=587`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_STARTTLS=true`); Mailpit в prod
не запускается; пока SMTP не настроен, адрес тестового пользователя подтверждает оператор:
`make confirm-email EMAIL=...`. В prod демо-коды ФСП выключены автоматически. Демо-стенд с моком ФСП на сервере: добавьте в `.env`
`FSP_DEMO_CODES_PROD=true` (паспорта будут помечены как выпущенные на демо-стенде). Для реального API ФСП
задайте `FSP_BASE_URL` и `FSP_API_KEY`.

## Тест на грейд и категории
- **Категория** = специализация (7 направлений) × грейд, подтверждённый тестом. Заявленный грейд — только
  гипотеза; в каталог кандидат попадает с подтверждённым.
- **Тест**: 15 заданий из банка 114 параметрических шаблонов (уровни 1–5, по стеку кандидата): числа, код и
  варианты ответа генерируются заново, сложность задаёт шаблон. Уровень оценивается моделью IRT (3PL,
  EAP): грейд подтверждён при θ ≥ g − 0.5, «уверенно» — при θ ≥ g + 0.5. Подробно — [`docs/assessment.md`](docs/assessment.md).
- **Повторы**: не сдал — сразу тест на грейд ниже; тот же грейд — через 14 дней; смена грейда — раз в
  90 дней; после уверенного результата 14 дней доступен тест на грейд выше.
- **Регулярные задачи**: раз в неделю — короткая задача от работодателя своей специализации; ответ
  обновляет актуальность профиля, компания оценивает его и может пригласить автора.

## Оценка качества
`make evaluate` — воспроизводимая процедура на синтетических данных со скрытой истиной
([`docs/validation.md`](docs/validation.md)). Основные результаты (1000 кандидатов, 40 вакансий):

| Метрика | IT Match | Для сравнения |
|---|---|---|
| Грейд совпал / ошибка не больше одного грейда / завышен | 70 % / 99,3 % / 3,7 % | — |
| Корреляция оценок уровня в двух разных тестах | 0,83 | — |
| Слабый кандидат с ответами 20 утёкших тестов сдал Middle | 21 % (без утечки 15 %) | единый тест: 100 % |
| Precision@10 подбора / nDCG@10 | 77,5 % / 0,83 | выдача по резюме: 64,8 % / 0,75 |
| Переоценённые кандидаты в топ-10 | 4 % | выдача по резюме: 27 % |

## ФСП, категории и паспорт навыков
- **Привязка ФСП**: кандидат вводит ID спортсмена, ФСП присылает одноразовый код на почту владельца
  аккаунта (10 минут, 5 попыток). Один аккаунт ФСП — один профиль (уникальный индекс в БД).
  Интеграция идёт через интерфейс `FspClient`: сейчас это мок `fsp-mock`, реальный API ФСП подключается
  заменой реализации. `FSP_DEMO_CODES=true` (только dev) показывает код в интерфейсе. Лимиты: запросы
  кода — по пользователю и по аккаунту ФСП, подтверждения — по пользователю; в моке — суточный лимит
  неудачных попыток на аккаунт.
- **Категории ФСП**: дисциплина ФСП x уровень (высший / продвинутый / базовый) по лучшему результату
  и разряду, с обоснованием; поднимают кандидата внутри категории «специализация × грейд» и доступны
  работодателю как фильтр. Профиль без истории ФСП — штатный случай: ранжирование по тесту и навыкам.
- **Паспорт навыков**: снимок профиля с подписью Ed25519, действует год. Проверка — публичная страница
  `/passport/<id>` или самостоятельно по ключу `GET /api/v1/public/passport-key`. Имя — только по выбору
  кандидата и из ФСП (подтверждённое); анонимный паспорт обобщает достижения. Должность, грейд и навыки
  помечены как заявленные кандидатом. Перевыпуск, отвязка ФСП и изменение данных ФСП отзывают прежний
  паспорт; по отозванному паспорту публично виден только факт отзыва.

## Автозаполнение профиля и ИИ
- **Из анкеты ФСП**: после привязки аккаунта (код из письма ФСП) — одной кнопкой подтягиваются имя, город,
  специализация, стек, контакты и сильнейшие результаты соревнований. По одному ID чужую анкету не получить:
  данные запрашиваются только для подтверждённого аккаунта, каждое чтение — в аудите.
- **Из резюме** (PDF с текстовым слоем или DOCX, до 5 МБ): алгоритм на правилах находит имя, должность, грейд,
  стаж, роли, софт-скиллы, город, формат, зарплату, контакты, раздел «О себе» и навыки по справочнику (с синонимами: golang,
  postgres, k8s). Файл не сохраняется; тип проверяется по содержимому, есть защита от zip-бомб.
- **ИИ (необязательно)**: суперадмин подключает модель в интерфейсе (`/admin/ai`): любой сервис с
  OpenAI-совместимым API (`/chat/completions`) — OpenAI, YandexGPT через совместимый шлюз, DeepSeek,
  OpenRouter, локальные Ollama/vLLM/LM Studio — или Anthropic. Ключ хранится зашифрованным, наружу — только
  последние символы; адрес проверяется (https, без служебных адресов стенда и метаданных облака; http — только
  для локальной модели, `AI_ALLOW_HTTP`). Активна одна модель; `ANTHROPIC_API_KEY` в `.env` — запасной вариант.
  Кандидат отмечает «Разобрать с помощью ИИ» — текст резюме уходит в выбранную модель **без контактов**.
  Ответ ограничен схемой и справочником; при любой ошибке работает алгоритм.
- Результат — черновик: кандидат видит «было → станет», выбирает поля (пустые отмечены сразу) и сохраняет сам.

## Подбор и выход на контакт
- **Без вакансии** кандидаты внутри категории ранжируются по силе подтверждённого профиля: тест 60,
  ФСП 25, актуальность 15. **Под вакансию** — соответствие 0–100 %: категория 30, близость уровня по тесту
  к грейду вакансии 20, навыки 20 (подтверждённые тестом — полностью, заявленные — наполовину), ФСП 10,
  описание 5, актуальность 5, формат и город 5, зарплата 5. По кнопке «Почему» — вклад и пояснение каждого
  фактора. Подробно — [`docs/matching.md`](docs/matching.md).
- **Приглашение** не требует вакансии: должность, описание, грейд, формат, вилка «от–до» (обязательна),
  способ связи. Статусы: отправлено → просмотрено → принято / отклонено (а также отозвано и истекло через
  14 дней). Одно открытое обращение на пару «компания — кандидат», после отказа — пауза 30 дней.
- **Отклик** кандидата на опубликованную вакансию — дополнительный сценарий; контакты уходят компании сразу.
- **Собеседование** — по принятому приглашению или отклику: 1–3 варианта времени, формат и руководитель;
  итог отмечается после встречи, отзыв видит кандидат. **Оффер** — по успешному собеседованию.
- До согласия кандидат анонимен; после — компания видит имя и контакты, каждое раскрытие — в журнале.

## Рост и зарплаты
- **Радар зарплат**: для грейда и навыков кандидата — вилки похожих вакансий (середина вилки), реальные
  офферы платформы и ожидания других кандидатов того же уровня: квартили 25/50/75 % и где ожидания
  кандидата («ниже рынка», «в рынке», «выше рынка»). Там же — вилки вакансий с тем же стеком по всем грейдам.
- **Путь роста**: навыки, которые чаще всего требуют вакансии следующего грейда и которых нет в профиле
  (с долей вакансий), сильные стороны, медиана зарплаты сейчас и на следующем грейде, следующий шаг в ФСП.
- **Рынок для работодателя**: в форме вакансии — типичная вилка для выбранного грейда и стека и где
  середина вилки компании.
- **Обезличенность**: распределение показывается только для групп от 5 значений, а данные компаний
  (вилки, офферы) — только если в группе не меньше 3 компаний: по медиане нельзя восстановить вилку
  одной компании или зарплату одного человека. Значения округлены до тысячи.

## Каталог и офферы
- **Статус поиска**: «Активно ищу», «Рассматриваю предложения», «Не ищу». Статус виден в каталоге и
  фильтруется; «Не ищу» убирает профиль из каталога и закрывает новые офферы.
- **Каталог** видят одобренные компании (по умолчанию — сразу после регистрации): категории
  «специализация × грейд» со счётчиками и анонимные карточки — без имени, контактов, ID ФСП и названий
  соревнований; кандидат может скрыть ожидания по зарплате, достижения ФСП и «о себе».
  Скрытые кандидаты в каталог не попадают (и на уровне RLS).
- **Оффер** — по успешному собеседованию, условия по умолчанию из приглашения, вилка обязательна, ответ — 7 дней. Повтор запроса
  с тем же `Idempotency-Key` не создаёт дубль; на пару вакансия-кандидат — один неотвеченный оффер;
  после отказа кандидата повторный оффер от компании — не раньше чем через 30 дней; не больше 50 офферов
  компании в сутки. Блокировка компании отзывает её неотвеченные офферы.
- **Контакты**: принимая приглашение (или откликаясь), кандидат передаёт снимок имени и контактов,
  зашифрованный с привязкой к обращению; каждый просмотр — в журнале.

## Почта и уведомления
- **Регистрация** не выдаёт, занят ли адрес: ответ всегда «проверьте почту», хеш пароля считается в обоих
  случаях. Владелец занятого адреса получает письмо «аккаунт уже есть» (или новую ссылку, если почта ещё
  не подтверждена). Вход — только после подтверждения почты.
- **Ссылки из писем** одноразовые (подтверждение — сутки, сброс пароля — час), в БД хранятся хешами; новая
  ссылка гасит прежние. Токен передаётся во фрагменте `#token=...`: он не уходит на сервер и в логи прокси,
  а страница сразу убирает его из адреса. Подтверждение — по кнопке: почтовые сканеры, открывающие ссылки
  сами, не подтвердят чужой аккаунт. Сброс пароля завершает все сессии.
- **Уведомления**: кандидату — о приглашении, собеседовании и оффере, компании — об отклике, ответе
  кандидата и решении модератора.
  Письма без персональных данных другой стороны: контакты — только в кабинете.
- **Доставка**: письмо ставится в очередь (`outbox_messages`) в транзакции действия и отправляется worker:
  ответ API не зависит от почтового сервера. Параметры письма зашифрованы и стираются после отправки;
  адрес определяется в момент отправки (заблокированным письма не уходят); сбой почты — повтор с паузой
  до 8 попыток. Канал — интерфейс `Notifier` (сейчас SMTP; Telegram подключается новой реализацией).
- Лимит писем на один адрес — 3 в час (защита чужого ящика от «почтовой бомбы»).

## Модерация
- **Вход администратора** — пароль и код TOTP (RFC 6238). Подключить аутентификатор можно только
  с одноразовым кодом подключения (сутки), который выдаёт CLI: знания пароля для этого мало. Секрет
  хранится зашифрованным, код нельзя использовать повторно, после 5 неверных кодов подряд вход
  блокируется на 15 минут; сессия администратора — не дольше 12 часов без продления, сессии без 2FA
  не продлеваются. Потерян телефон — `make reset-admin-2fa EMAIL=...` (только с сервера).
- **Вакансии**: блокировка скрывает вакансию из выдачи и отзывает неотвеченные офферы по ней;
  разблокированная возвращается работодателю черновиком на проверку.
- **Пользователи**: поиск по email и роли; блокировка закрывает вход и завершает все сессии.
  Администраторов блокирует только суперадмин, себя заблокировать нельзя.
- **Аудит**: каждое действие модератора — с обязательной причиной; в журнале также входы, 2FA, офферы,
  раскрытие контактов и действия с ФСП. Журнал только на вставку (и на уровне БД).

## Безопасность
- Секреты только в `.env` (генерируются локально, права 600); в репозитории — `.env.example` без значений.
- gitleaks в pre-commit и CI; в prod приложение не стартует со слабыми секретами.
- БД не публикует порты; приложение работает под ролью без прав на DDL; владелец схемы — только для миграций.
- Row Level Security: кандидат видит и меняет только свой профиль, работодатель — вакансии своей компании
  (вторая линия после фильтров репозиториев); журнал аудита только на вставку.
- Администраторы входят только со вторым фактором (TOTP); без кода пароль сессию не даёт.
- Лимиты запросов общие для всех процессов и реплик (PostgreSQL, ключи — хешами), IPv6-клиенты
  считаются по сети /64.
- Адрес языковой модели проверяется и при сохранении, и перед каждым запросом по адресам, в которые
  резолвится имя: loopback, метаданные облака, служебные сервисы и (по умолчанию) частные сети закрыты —
  не обойти ни доменом, ведущим на 127.0.0.1, ни десятичной записью IP. Частные сети для on-prem
  модели — `AI_ALLOW_PRIVATE_NETWORK=true`.
- Пароли — argon2id; refresh-токены хранятся хешами, ротируются атомарно, повторное использование
  отзывает цепочку; лимит попыток входа и по IP, и по аккаунту.
- Удаление аккаунта кандидата (отзыв согласия, 152-ФЗ) — с подтверждением паролем: профиль, привязка ФСП,
  паспорт, собеседования и офферы удаляются каскадом в БД, сессии завершаются; в журнале остаётся только
  факт удаления без персональных данных. Аккаунт компании удаляется через поддержку.
- Каталог кандидатов на уровне БД доступен только одобренным компаниям и без скрытых профилей;
  блокировка компании модератором блокирует и её вакансии.
- Имя и контакты кандидата шифруются в БД (AES-256-GCM, ключ `FIELD_ENCRYPTION_KEY`), шифртекст
  привязан к полю и владельцу.
- В prod каждый сервис проверяет силу только своих секретов и не стартует со слабыми.
- Тесты IDOR перечисляют все эндпоинты автоматически: новый маршрут без проверки прав уронит CI.
- Контейнеры: non-root, read-only FS, `cap_drop: ALL`, `no-new-privileges`, лимиты ресурсов.
- Caddy: HTTPS, HSTS, CSP, X-Frame-Options, лимит тела запроса.

## Нагрузка и масштабирование
Замер `make load` на ноутбуке (Docker Desktop), 2000 кандидатов в каталоге, 20 одновременных
пользователей на сценарий, через прокси Caddy:

| Сценарий | 1 процесс api (dev) | 4 процесса api |
|---|---|---|
| Каталог с подбором по вакансии | 264 запр/с, p95 105 мс | 420 запр/с, p95 73 мс |
| Каталог без подбора | 337 запр/с, p95 83 мс | 480 запр/с, p95 72 мс |
| Профиль кандидата | 826 запр/с, p95 27 мс | 1690 запр/с, p95 22 мс |
| health | ~12 тыс. запр/с | ~41 тыс. запр/с |

Ошибок — 0. До оптимизаций подбор давал 21 запр/с при p95 1,2 с: расчёт шёл заново на каждый
запрос и занимал единственный процесс.

- **Подбор**: рейтинг вакансии кэшируется на минуту (страницы листаются без пересчёта и в стабильном
  порядке, правка вакансии сбрасывает кэш); данные вакансии для факторов готовятся один раз.
- **Процессы**: в prod api работает в `API_WORKERS` процессах (по умолчанию 2) — CPU-задачи не
  останавливают остальные запросы; argon2 при входе и регистрации — в отдельных потоках.
- **Лимиты запросов — в PostgreSQL** (`RATE_LIMIT_BACKEND=postgres`): общие для всех процессов и реплик,
  скользящее окно, одна атомарная команда на проверку (~3,6 тыс. проверок/с при медиане 4 мс);
  ключи хранятся хешами, старые счётчики удаляет worker. Можно добавлять процессы и реплики api.
- **Worker** безопасно запускать в нескольких экземплярах: синхронизация ФСП захватывает пачки
  (`FOR UPDATE SKIP LOCKED` + аренда на 10 минут), очередь писем — так же, остальные задачи идемпотентны.
- **Соединения с БД**: `DB_POOL_SIZE` на процесс (+10 временных); всего держите ниже `max_connections`
  PostgreSQL (100): `API_WORKERS × (DB_POOL_SIZE + 10) + worker`.
- Дальше при росте: Redis или pgbouncer, read-реплика для каталога, предрасчёт рейтинга в worker.

## Разработка
- Ветки `feature/*`, `fix/*`; в `main` — только через pull request. Коммиты — conventional commits.
- CI (GitHub Actions): gitleaks по всей истории, линт и тесты бэкенда (с PostgreSQL), мока ФСП
  и фронтенда, аудит зависимостей (pip-audit, npm audit), сквозной прогон стека в Docker (`make verify`).
- Перед коммитом: `make test` и `make secrets-check`.
- Проект в папке iCloud/OneDrive? Синхронизация создаёт копии вида `config 2.py`; `make dev` их
  обнаружит и остановится — удалите копии (`make check-dupes` покажет список) или перенесите проект.

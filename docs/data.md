# Данные: таблицы, RLS, роли, шифрование

PostgreSQL 16. Все ключи — UUID. Схема меняется только миграциями Alembic
(`backend/migrations/versions`), применяет их контейнер `migrate` под ролью-владельцем.

## Row Level Security

Приложение перед запросами задаёт контекст транзакции (`app/db/session.py`):

```sql
SELECT set_config('app.user_id', '<uuid>', true), set_config('app.role', 'candidate', true)
```

Политики строятся функциями из `backend/migrations/rls.py`:

- `owns_profile(col)` — строка принадлежит пользователю из контекста;
- `member_of(company_col)` — пользователь состоит в компании;
- `PRIVILEGED` — роль `admin` или `system`.

Что гарантирует БД, даже если код ошибётся с фильтром:

- кандидат видит и меняет только свой профиль, навыки, привязку ФСП, достижения и паспорт;
- работодатель видит профили, только если компания одобрена, и только нескрытые; изменить не может;
- черновики, закрытые и истёкшие вакансии видны только своей компании;
- приглашения и отклики, попытки теста, ответы на задачи, жалобы и отметки «просмотрено» видят только
  их участники;
- офферы и собеседования видят только их стороны (кандидат и сотрудники компании);
- привязку ФСП (ID спортсмена деанонимизирует кандидата) видит только владелец;
- без контекста не видно ничего.

Роль `system` — для фоновых задач, публичной проверки паспорта и агрегатов радара зарплат.
Агрегаты читаются в блоке `system_scope(session)`: наружу уходят только медианы и счётчики с порогом
k-анонимности, после блока восстанавливается контекст пользователя.

Тесты RLS — `backend/tests/test_rls_postgres.py`: прямой SQL под ролью приложения.

## Роли БД

| Роль | Права | Кто использует |
|---|---|---|
| владелец схемы (`DB_OWNER_USER`) | DDL, миграции | только контейнер `migrate` |
| приложение (`APP_DB_USER`) | только DML на таблицы `public`; без DDL, без суперпользователя, без доступа к служебным БД; `audit_log` — только `INSERT`/`SELECT` | `api`, `worker` |

Права выдаёт `app/db/provision.py` после миграций (идемпотентно, синхронизирует пароль после смены
`.env`). Проверка прав — `make check-db` (входит в `make verify`).

## Шифрование полей

AES-256-GCM, ключ `FIELD_ENCRYPTION_KEY` (32 байта hex). Каждый шифртекст привязан к «контексту»
(associated data) — полю и владельцу. Поэтому шифртекст нельзя переставить в чужую строку или поле:
расшифровка не пройдёт.

| Поле | Контекст |
|---|---|
| `candidate_profiles.full_name_enc`, `contacts_enc` | `profile_field_context(поле, user_id)` |
| `users.totp_secret_enc` | `user_field_context("totp", user_id)` |
| `offers.contact_name_enc`, `contacts_enc` | `offer_field_context(поле, offer_id)` |
| `ai_providers.api_key_enc` | `ai_key_context(provider_id)` |
| `outbox_messages.payload_enc` | `outbox_payload_context(message_id)` |

Смена ключа требует перешифровки этих полей (скрипта ротации пока нет — см. бэклог в [development.md](development.md)).

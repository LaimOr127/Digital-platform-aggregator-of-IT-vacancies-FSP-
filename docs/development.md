# Разработка: правила, процесс и состояние проекта

Документ для разработчиков команды и новых участников: что строим, этапы и текущее состояние, правила
работы и как проверить, что ничего не сломано. Остальная документация — в оглавлении `docs/README.md`.

## 1. Что за проект

**IT Match** — отраслевой агрегатор ИТ-вакансий для хакатона с Федерацией спортивного программирования
(ФСП). Обратная механика: кандидат проходит опрос и тест на заявленный грейд и попадает в категорию
«специализация × подтверждённый грейд»; работодатель выбирает категорию или вакансию, видит анонимные
карточки с процентом соответствия и объяснением и сам направляет приглашение с описанием и обязательной
вилкой (вакансия не обязательна). Контакты кандидата открываются после принятия приглашения или его
собственного отклика; дальше собеседование и оффер. Достижения ФСП поднимают кандидата в категории.

- Исходный план: `docs/PLAN.md` — **только чтение** (права `r--r--r--`, не менять и не снимать флаг).
  Отклонения от плана и статус ведём здесь и в `README.md`.
- Техническое задание хакатона (PDF у владельца) — главный источник требований; соответствие пунктам ТЗ 3.4
  по документации — в `docs/README.md`. Где план и ТЗ расходятся, прав ТЗ (например: категории —
  специализация × грейд по тесту, а не по ФСП; компании без премодерации).
- Команда: 3 человека (2 разработчика, системный аналитик). Владелец репозитория — LaimOr127.
- Репозиторий: https://github.com/LaimOr127/Digital-platform-aggregator-of-IT-vacancies-FSP-

## 2. Обязательные правила

### Git
- Conventional commits: `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`, `perf:`; сообщение на русском.
- Никогда не пушить в `main`. Ветки `feature/…`, `fix/…`, `refactor/…`, вливание — через pull request.
- Один коммит — одна логическая задача. Перед коммитом — просмотреть весь diff.
- Не коммитить `.env`, ключи, сгенерированное (`dist`, `coverage`, `__pycache__`, `node_modules`).
- Перед push: `make test`, `make verify` (на поднятом стеке), `make secrets-check`.

### Код
- Файл — не больше 300 строк; функция делает одно дело; повтор логики 2+ раза — выносить.
- Без `console.log` и `print()` в рабочем коде, без эмодзи в коде.
- `const` по умолчанию, иммутабельность; понятные имена без сокращений.
- Прежде чем менять файл — прочитать его целиком. Писать в стиле окружающего кода
  (плотность комментариев, именование). Комментарии и тексты интерфейса — на русском.
- Документация — в `README.md` и `docs/`; поведение изменилось — документ обновляется в том же PR.

### Тесты
- Покрытие не ниже 80 % (сейчас ~95 % и на бэке, и на фронте). Сначала тест, потом реализация.
- Внешние зависимости (ФСП, SMTP, модели ИИ) в тестах подменены. Тест независим и проверяет одно поведение.
- Задача не готова, пока не проходят `make test` и `make verify`.

### Безопасность
- Никаких секретов в коде; только `.env` (создаёт `make env`), в репозитории — `.env.example` без значений.
- Литералы паролей в тестах ловит gitleaks — используйте `tests.helpers.PASSWORD`.
- Валидировать вход на сервере; не логировать токены, пароли и персональные данные.
- Новый эндпоинт — с проверкой роли (`require(Action.…)`) и тестом на чужую роль и чужую строку.
- Новая таблица с данными пользователей — сразу с RLS и тестом в `test_rls_postgres.py`.

## 3. План по этапам и текущее состояние

Статусы: **готово** — реализовано, покрыто тестами, проверено в браузере; **частично**; **нет**.
Все этапы влиты в `main`; история этапов — в закрытых pull request #2–#10.

### Этап 2. ФСП и паспорт навыков — готово (PR #2)

## 6. Как работать

```bash
git checkout -b feature/<задача>      # от актуального main
make env && make dev                   # стек на http://localhost:8088, письма — http://localhost:8025
# ... изменения + тесты ...
make test && make verify && make secrets-check
git commit -m "feat(область): что сделано"
git push -u origin feature/<задача>
gh pr create --base main
```

- После изменения API: `npm run gen:api` во `frontend/` при запущенном стеке (или скопировать схему
  `http://localhost:8088/api/openapi.json` через openapi-typescript), затем `types.ts` и `endpoints.ts`.
- После изменения кода в контейнерах: `make up S="api web"` (dev-api перезагружается сам при правке
  `backend/app`, фронт нужно пересобрать).
- Проверка в браузере: зарегистрировать пользователя → письмо в Mailpit → вход. Работодателю нужен
  администратор (`make create-admin`) и одобрение компании в `/admin`. Access-токен живёт 15 минут.
- Готово — когда: тесты зелёные, покрытие не упало, смоук проходит, UI проверен на десктопе и 375 px,
  README и `docs/` обновлены, если поменялось поведение.

## 7. Подводные камни

- **iCloud.** Репозиторий лежит в `~/Documents` с синхронизацией iCloud: появляются копии `file 2.py`
  (ломают Alembic и git) — `make check-dupes`; Docker падает с `Resource deadlock avoided`, если файлы
  выгружены — прочитать их (`find backend frontend -type f -exec cat {} + > /dev/null`). Правки через
  `sed -i` иногда обнуляют файл — проверяйте размер после правки.
- **gitleaks и iCloud.** Внутри контейнера `git log -p` по репозиторию из iCloud падает (bus error), и
  gitleaks пишет «0 commits scanned, no leaks found». `make secrets-check` поэтому сканирует клон во
  временной папке и считает «0 коммитов» ошибкой. Литералы паролей в тестах CI находит по всей истории.
- **Лимиты в PostgreSQL переживают перезапуск.** Частые прогоны смоука дают `429`; сброс в dev —
  `TRUNCATE rate_limit_buckets` (команда в `docs/operations.md`).
- **Демо-кандидаты (`seed-demo`) без входа** — для входа регистрируйте своих пользователей.
- **Справочник навыков** в PostgreSQL больше, чем в SQLite-тестах: проверки не должны зависеть от его размера.
- **Новая таблица** в PostgreSQL-тестах — добавить в `_TRUNCATE` (`backend/tests/dbsetup.py`).
- **Переменные окружения** доходят до контейнеров, только если перечислены в `deploy/common.yml`
  или `compose.<сервис>.yml`.
